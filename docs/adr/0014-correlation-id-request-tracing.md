# 0014 - Correlation-ID Request Tracing

**Status:** Accepted

## Context

When diagnosing errors or latency spikes in production, the API logs for a single HTTP request are interleaved with logs from concurrent requests. Without a request-scoped identifier, it is impossible to group all log lines, error responses, and trace spans that belong to the same incoming call. The existing OpenTelemetry tracing (ADR-0009) provides distributed span correlation, but does not surface a human-readable request identifier in plain log output or in error responses returned to the client.

The system has two layers where a correlation ID must be visible:

1. **API logs and error responses** -- so backend engineers can grep for a specific request.
2. **Client-facing error responses** -- so the web client (or any API consumer) can report a correlation ID to support, and support can look it up in the logs.

The correlation ID must flow end-to-end: from the web client, through nginx, into the NestJS API, and back out through the response headers. It must also be attached to OpenTelemetry spans so that the ID appears in the trace backend alongside the existing span attributes.

Three approaches were considered:

1. **AsyncLocalStorage with NestJS middleware:** generate or accept a `X-Correlation-ID` header in a NestJS middleware, store it in Node.js `AsyncLocalStorage`, and read it from logging, error-handling, and tracing code without threading it through function signatures.
2. **Request-scoped NestJS providers:** use NestJS's built-in request-scoped dependency injection to inject a correlation service into every controller and service. This adds per-request DI overhead and requires every consumer to declare an injection token.
3. **Explicit parameter passing:** pass the correlation ID as an argument through every controller, service, and utility function. This is safe but verbose and would touch most API files.

Evidence:

- `apps/api/src/common/correlation-id.ts`: defines the `AsyncLocalStorage` store and the `getCorrelationId()` accessor.
- `apps/api/src/common/correlation-id.middleware.ts`: NestJS middleware registered on all routes in `AppModule.configure`. Reads `X-Correlation-ID` or `X-Request-ID` from the incoming request, generates a UUID v4 when neither is present, sets the response header, and runs the rest of the request inside the async-local store.
- `apps/api/src/common/correlation-id.logger.ts`: `CorrelationIdLogger` extends NestJS `ConsoleLogger` and prepends `[cid:<id>]` to every log line when a correlation ID is active.
- `apps/api/src/common/problem-details.filter.ts`: the global exception filter now reads the correlation ID from the store and sets `X-Correlation-ID` on every error response so clients can report it.
- `apps/api/src/instrumentation.ts`: the HTTP instrumentation `requestHook` reads the `X-Correlation-ID` header from the incoming request and sets `app.correlation_id` on the OTel span.
- `nginx/nginx.conf` and `nginx/nginx-dev.conf`: both pass `X-Correlation-ID` from the client to the API via `proxy_set_header X-Correlation-ID $http_x_correlation_id`.
- `apps/web/src/api/client.ts`: `apiFetch` generates a UUID v4 `X-Correlation-ID` header on every outgoing request. `ApiError` carries an optional `correlationId` extracted from the response header.

## Decision

Use Node.js `AsyncLocalStorage` as the per-request correlation store, populated by a NestJS middleware that runs on every route. The correlation ID is a UUID v4 generated by the API when the incoming request does not carry one. The ID flows to three consumers:

1. **Structured logging:** `CorrelationIdLogger` prepends `[cid:<id>]` to every log line.
2. **Error responses:** the problem-details filter sets `X-Correlation-ID` on every error response.
3. **OpenTelemetry spans:** the HTTP instrumentation request hook sets `app.correlation_id` on the server span.

nginx is configured to pass the `X-Correlation-ID` header through to the API so the web client can supply its own ID. The web client (`apiFetch`) generates a UUID v4 per request and reads the ID back from error responses.

## Alternatives Considered

- **Request-scoped NestJS providers:** avoids `AsyncLocalStorage` but introduces per-request DI overhead (NestJS creates a new module tree per request). Overkill for a single string value that most code only reads.
- **Explicit parameter passing:** no hidden state, but requires changing the signature of every service method and utility that might need the ID. The AsyncLocalStorage approach lets new consumers call `getCorrelationId()` without touching callers.
- **OTel context-only:** ADR-0009 already provides trace context, but OTel context propagation does not surface in plain `console.log` output or in error response headers. The correlation ID complements tracing by being visible in log aggregation and client-facing error payloads.

## Consequences

- Every API request has a UUID v4 correlation ID visible in logs (`[cid:<id>]`), error responses (`X-Correlation-ID` header), and OTel spans (`app.correlation_id` attribute).
- The correlation ID flows end-to-end: web client -> nginx -> API -> response. Support can ask a user for the correlation ID from an error message and look it up in the logs or the trace backend.
- `AsyncLocalStorage` is a Node.js built-in (no external dependency) and is safe for single-threaded async request handling. Care must be taken if the API ever moves to worker threads; the store is per-thread.
- The middleware is registered first in `AppModule.configure`. Any future middleware that needs the correlation ID must be registered after `CorrelationIdMiddleware`.
- The web client sends `X-Correlation-ID` on every request. Non-browser clients (curl, API keys) can also supply the header; when absent, the API generates one.
